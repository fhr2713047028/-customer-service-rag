## 1. 工作方式（用户要求，贯穿全程）

1. **听用户指挥**：每个模块开始前等待用户指令，不擅自推进、不提前实现（RAG/Agent/Redis/监控都不得提前）。
2. **每模块交付三件套**：文件变更清单 + Windows 运行命令 + 真实测试结果（禁止虚构；失败先定位原因再最小修复）。
3. 等用户验证通过后再继续下一个模块。
4. 每个实施阶段产出 `docs/phase-XX-*.md`，含：运行方法、测试方法、预期结果、常见错误排查。
5. **项目定位（2026-10-30 确认）**：本项目是**简历项目，不实际投入使用**。部署（Docker 生产化）相关内容推迟到最后（阶段 10）一次性进行，此前不做任何部署工作；开发期本地数据库沿用现有容器仅作开发便利。阶段 10 的 HTTPS/CI/备份演练降级为可选加分项，不强制。

## 4. 分层压测方案（阶段 9 执行）

### 4.1 三条测试路径（严格分开，不混算）

| 路径 | 定义 | 测量指标 |
|---|---|---|
| P1 数据库精确查询 | `GET /orders/{order_no}` 与商品/物流结构化接口（无任何外部调用） | P50/P95/P99、QPS、错误率 |
| P2 FAQ 混合检索（不含 LLM 生成） | `/chat` 政策类问题，FTS+向量+RRF+Embedding 外部调用，`answer_type=faq` | 同上 + Embedding 调用耗时分布 |
| P3 完整 RAG 问答 | `/chat` 知识文档/组合问题，含 LLM 生成，`answer_type=generated` | **TTFT、完整响应延迟、吞吐量、错误率** + 成本 |

- P3 **不设硬指标**；**不得**以 TTFT 达标推论完整回答 P99 达标；任何"达到目标"的表述必须附原始数据。

### 4.2 目标成立所需的条件（如实声明）

- **测试环境**：独立压测环境；app 与 DB 部署方式、服务器规格逐项记录（规格待定）；压测机与目标机分离。
- **数据规模**：按 database_design.md 第 6 节初始建议规模的合成数据（标注生成方式），**不代表生产规模下目标依然成立**。
- **外部依赖**：P2/P3 依赖硅基流动与 DeepSeek 的真实可用性与限速 —— 结果只对该时点、该供应商成立。
- **负载假设**：四类任务 60%（P1 类）/ 25%（P2 类）/ 10%（P3 类）/ 5%（组合+异常：多意图问句、无效订单号 404、无 token 401），**仅用于初始压测，不代表真实电商流量**；四类任务在 locustfile 中独立定义，每任务恰好一次 HTTP 请求、互斥不重复计数；±10% 敏感性测试。
- **通过标准**：P1/P2 在目标 QPS 下 P99 < 500ms 且错误率 < 0.1%；P3 只记录与归因（检索/Embedding/LLM 各占多少）。

### 4.3 步骤与报告

1. 阶梯加压 50 → 100 → 200 → 300 QPS，每档 ≥ 5 分钟；任一档 P1/P2 失败即停止并记录瓶颈。
2. 每档记录：三条路径各自延迟分位、错误分布、DB 连接池水位、CPU/内存、慢查询、Embedding/LLM 耗时分布、TTFT。
3. 报告模板（禁止虚构，必须含原始数据）：环境规格 / 数据规模与合成方式 / 负载配比 / 各档分路径延迟分位表 / 错误分布 / 资源曲线 / 外部 API 实测耗时与成本 / 瓶颈归因 / 下一步优化项。
4. 优化顺序（杠杆从大到小）：提高模板与 FAQ 命中率（请求留在 P1/P2）→ 高频 FAQ 缓存（Redis 在此评估）→ LLM 流式（仅当完整链路延迟成为业务问题）→ 连接池调优 → 水平扩容。

### 4.4 预算 0 元下的测试策略（已确认）

- **P1**：无外部调用，真实测量，不产生费用。
- **P2**：优先使用现有免费 API 额度测真实 Embedding；无额度时用**本地 Mock Embedding**（确定性本地向量生成器，标注 Mock）测量 FTS + HNSW + RRF 组件性能与并发能力。报告注明："P2 含真实 Embedding API 的端到端结果未测（预算 0 元），以下为 Mock Embedding 下检索组件性能"。
- **P3**：无额度时用**本地 Mock LLM**（标注 Mock）——只能测量本系统非模型部分的开销（提示词组装、HTTP 客户端、解析、并发上限），**不产生 TTFT 与真实生成质量的任何结论**；真实 API 下的 TTFT/完整延迟/吞吐/成本留待有额度或预算批准后补测。
- **三条红线**：Mock 与真实 API 的结果分表呈现；每条结论标注数据来源；**不得以 Mock 数据声称真实 RAG 链路达到任何性能目标**。
- **用量记账**：即便使用免费额度，也记录每次调用的 token 数与耗时（API 响应 usage 字段），为未来预算核算留数据。

6. /metrics 访问控制的具体方式：开发期仅内网 + 文档说明；生产期反代拦截（阶段 10 落地）。
