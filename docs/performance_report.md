## 2. 三类性能测试结果（12.1 严格区分）

### 2.1 业务 API（20 用户 × 2 分钟，不调用任何模型）

**总请求 7129，意外失败 0，吞吐 59.4 RPS**

| 端点 | 请求数 | P50 | P95 | P99 |
|---|---|---|---|---|
| 订单列表 | 2363 | 8ms | 12ms | 16ms |
| 订单详情 | 1822 | 7ms | 12ms | 28ms |
| 商品关键词 | 1788 | 5ms | 10ms | 12ms |
| 物流查询 | 1156 | 6ms | 12ms | 18ms |

**结论：全部端点 P99 ≤ 28ms、错误率 0。** 5000 订单规模下复合索引与 trigram 索引工作正常；
连接池（10+10）在 20 并发下无排队迹象。**QPS>200、P99<500ms 对业务 API 在 20 并发下成立，更高并发未测（见第 4 节）。**

### 2.2 检索链路（10 用户 × 2 分钟，LLM=Mock 隔离，Embedding=真实）

**总请求 1278，失败 0，吞吐 10.7 RPS；端到端 P50=370ms / P95=450ms / P99=490ms**

| 环节（Prometheus 实测平均） | 耗时 |
|---|---|
| 数据库查询 | 1.5ms |
| 关键词 + 向量检索（含 RRF） | 12.1ms |
| **Embedding API（真实 BGE-M3）** | **293.9ms** |

**结论：检索链路 P99=490ms 的瓶颈是外部 Embedding API 往返（占 60%+），本地检索本身仅 12ms。**
该结果包含真实 Embedding（已标注）；若用 Mock Embedding 另行标注，本地检索管线预计远低于此值。

### 2.3 完整 RAG（2 用户 × 2 分钟，真实 DeepSeek）

**总请求 70，失败 0，吞吐 0.58 RPS；端到端 P50=1.7s / P95=2.7s / P99=2.7s**

| 环节（Prometheus 实测平均） | 耗时 |
|---|---|
| 数据库 + 检索 | ~14ms |
| Embedding API | 293.9ms |
| **LLM 生成（真实 DeepSeek）** | **1235.6ms（平均）** |

**结论：完整 RAG 的延迟几乎全部由真实模型生成主导。**
- v1 为非流式输出，**TTFT 指标不适用**：完整响应延迟即端到端延迟；
- **不得将任何数字宣称"完整 RAG 的 P99 < 500ms"——本测试明确不满足，且预期就不满足**；
- 模型持续可用：2 用户下 70 次调用 0 限流 0 错误。

### 2.4 混合分布（20 用户 × 2 分钟，四类任务 60/25/10/5 权重）

**总请求 4679，失败 42（全部为故意注入的 401/404 异常场景，意外失败 0），吞吐 39.0 RPS**

| 类型 | 实际请求占比 | 假设占比 | 说明 |
|---|---|---|---|
| 业务 API | 90.6% | 60% | 偏差原因：locust 权重按"用户数"分配，业务类等待时间短（0.1~0.5s）产生请求更快 |
| 检索 | 6.3% | 25% | 同上 |
| 完整 RAG | 1.3% | 10% | 同上（等待 1~3s + 生成 1.7s） |
| 组合+异常 | 1.8% | 5% | 同上；其中 42 次 401/404 为按设计的异常场景 |

**如实声明**：60/25/10/5 是"用户权重"假设而非请求占比目标；本脚本记录的是**实际请求分布**（12.2 要求）。若需请求占比逼近假设，应改按"任务权重 × 等待时间倒数"校准——留作后续优化项。

## 3. 瓶颈分析（12.2.8）

| 瓶颈 | 证据 | 影响路径 |
|---|---|---|
| **LLM 生成延迟** | 平均 1.24s，P99 2.7s | 完整 RAG 端到端 |
| **Embedding API 网络往返** | 平均 294ms | 所有知识库路径（检索/完整 RAG） |
| 数据库与本地检索 | 1.5ms / 12.1ms | **无瓶颈**（5000 订单下索引与连接池健康） |
| 应用自身开销 | 业务 API P99≤28ms | **无瓶颈** |

## 4. 有依据的优化方案（12.2.9，未实施，供对照测试使用）

| 方案 | 依据 | 预期收益 | 风险/成本 |
|---|---|---|---|
| LLM 流式输出（SSE） | 生成 1.24s 为最大单项 | 首字延迟可降至 <500ms 量级（**TTFT 指标才能成立**），感知延迟大幅下降 | 需改 chat 端点协议（前端已预留） |
| FAQ/热门问题缓存（Redis） | 25% 检索类问题重复度高 | 缓存命中路径延迟降至 ~10ms | 引入 Redis 与失效策略 |
| Embedding 批量化/本地化 | 294ms 为第二单项 | 批量接口分摊或本地 BGE-M3 部署可降至毫秒级 | 本地部署需 GPU/内存 |
| 水平扩容（多副本） | 应用无状态、业务路径无共享内存 | 吞吐线性扩展 | 部署复杂度 |

**对照测试方法（12.2.10）**：每项优化实施后，用本文件第 1 节的相同环境参数 + 相同 locust 命令重跑对应测试类，产出 `results/<name>_after_*.csv`，与本报告基线逐项对比并记录差异与原因。

## 5. 测试中遇到的问题（如实记录）

1. **locust gevent 环境无法运行 asyncio**：初版 on_start 连数据库取数据 → 协程从未执行、0 请求。修复：数据预生成 JSON（scripts/prepare_perf_data.py），locust 纯文件 IO；
2. **数据源指错**：prepare 脚本默认连原生 PG（5432，100 订单）而非容器库（5433，5000 订单）→ 订单号不匹配全 404。修复：`DATABASE_URL` 环境变量显式指向 5433；
3. **locust 2.x 的 `events.test_stop` 已不触发**：改用 `--csv-full-history` 的百分位列 + 分析脚本（scripts/analyze_locust.py）提取 P50/P95/P99；
4. **用户权重 ≠ 请求占比**：见 2.4 表，已如实记录偏差与原因；
5. Docker Desktop 隔日停机 → 压测前重启并等待健康检查。
